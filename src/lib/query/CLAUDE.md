- `conn.send()` for data queries (non-blocking, cancellable)
- `conn.query()` only for fast metadata queries
- `geometry_always_xy = true` set at DB init (DuckDB v1.5+ lon/lat axis order)
- `force_download_threshold = 2000000` set at DB init (httpfs downloads files <2MB in one shot instead of range-requesting)
- **OPFS-backed database** opened at boot. The URL-scheme path (`db.open({path: 'opfs://...'})`) silently no-ops on the pinned 1.33.1-dev53.0 build (DB stays in-memory and the next OOM still says "in-memory mode"), so the wiring registers the file via `db.registerFileHandle(name, null, DuckDBDataProtocol.BROWSER_FSACCESS, true)` first, then opens by registered name with `DuckDBAccessMode.READ_WRITE`. The OPFS file is pre-created via `navigator.storage.getDirectory().getFileHandle(name, {create: true})` because handle registration does not auto-create. Falls back to in-memory if `navigator.storage.getDirectory` is missing (private mode, older browsers, cross-origin isolation) or if `BROWSER_FSACCESS` is not exported by the bundled WASM build. When OPFS is active the boot log says `opened OPFS-backed DB "objex-duckdb.db"` and `opfsActive` is `true`; if you still see `Database is launched in in-memory mode` in OOM messages after editing this code, OPFS registration silently fell back and the warn line above will pinpoint why
- Memory tuning is **only** applied when OPFS spill is wired. With OPFS: `memory_limit='2GB'`, `threads = min(4, cores/2)`, `temp_directory='.tmp'` (resolved against the OPFS root). Without OPFS: leave `memory_limit` and `threads` at DuckDB defaults so queries can use the full WASM heap (~3 GiB). Capping below the heap ceiling without a spill target makes queries OOM **sooner** with no upside — a low cap (`900MB`) was tried and immediately reproduced the same OOM at the new cap rather than the heap. `preserve_insertion_order = false` is always set at boot since it skips full-result buffering on output, a real OOM source in both modes
- **OPFS requires Cross-Origin Isolation**: the dev server (and any production host) MUST send `Cross-Origin-Opener-Policy: same-origin` AND a COEP header. Without them `navigator.storage.getDirectory()` works but `FileSystemFileHandle.createSyncAccessHandle()` (called inside the DuckDB worker) throws `SecurityError`, OPFS open silently fails, and DuckDB falls back to MEMFS. `vite.config.ts` sets these under both `server` and `preview`; production hosts (Cloudflare Pages, Netlify, etc) need their own header config. The boot log shows `OPFS via registered handle` (or `OPFS via opfs:// scheme`) when wiring succeeded; if you see `all OPFS paths failed`, check the warn lines above
- **Use `Cross-Origin-Embedder-Policy: credentialless`, NOT `require-corp`**. With `require-corp` every cross-origin fetch (DuckDB httpfs reading S3 parquet, COG range reads, STAC API JSON) must come with a `Cross-Origin-Resource-Policy` header on the response. Public buckets like source.coop, raw AWS S3, and most STAC APIs do **not** send CORP, so the browser blocks the fetch and httpfs surfaces it as `HTTP 404 Not Found` (the file curl-fetches fine — the 404 is the browser blocking the request, not S3 returning 404). `credentialless` still grants `crossOriginIsolated = true` (so OPFS engages) but loads cross-origin resources without credentials and without requiring CORP. Caveat: Safari did not support `credentialless` until 17.6 — older Safari users will revert to in-memory DuckDB
- `DEFAULT_TARGET_CRS = 'OGC:CRS84'` (GeoParquet 1.1 canonical, equivalent to EPSG:4326 under always_xy)
- GeoParquet auto-conversion enabled (default) — columns read as `GEOMETRY('EPSG:...')`
- Legacy GeoParquet fallback: `enable_geoparquet_conversion = false` set per-connection when detected. The known CRS (from hyparquet metadata) is re-attached via `ST_SetCRS(ST_GeomFromWKB(...))` so downstream `ST_Transform` uses the 2-arg form
- **Init SQL ordering is load-bearing**: `SELECT * FROM duckdb_coordinate_systems()` must run BEFORE explicit `LOAD spatial` to warm the PROJ default CRS registry. Workaround for [duckdb-wasm#2199](https://github.com/duckdb/duckdb-wasm/issues/2199), do not reorder
- Use helpers from `utils/geometry-type.ts` (`parseGeometryTypeCrs`, `buildTransformExpr`, `wrapWkbWithCrs`, `isWgs84Crs`) instead of ad-hoc regex on type strings
- For `signed-s3` connections, use `resolveTableSourceAsync(tab)` so the resolved `fileUrl` / `ref` carries a presigned HTTPS URL (SigV4 query string). DuckDB's httpfs then fetches with `Range` only, skipping the `Authorization` preflight that breaks on GCS. Every `configureStorage` call site threads either `source.ref` (`getSchema`, `getRowCount`, `getSchemaAndCrs`, `detectCrs`) or the raw `sql` (`query`, `queryForMap`, `queryCancellable`, `queryForMapCancellable`) so `isHttpsSourceRef()` short-circuits the S3 SETs on every query path, not just the initial schema probe. The `isHttpsSourceRef` regex matches both bare refs and `https://` URLs embedded in `read_parquet('https://...')` SQL
- **Arrow DECIMAL handling**: DuckDB-WASM emits DECIMAL columns as Arrow `Decimal128` buffers whose values are either `BigInt` or `Uint32Array` little-endian words. `isNumericArrowType()` excludes DECIMAL so values go through the decimal path; `decimalScale()` parses **both** the DuckDB DESCRIBE form (`DECIMAL(10,2)`) **and** the Arrow `toString()` form (`Decimal[10e+2]`, precision `e` signed-scale) since `query()` / `queryCancellable()` derive `types` from `String(field.type)` on Arrow schema — never the DESCRIBE string. `formatDecimal()` then rewrites each cell to a scaled decimal string. Reviewed in v1.2+ after the initial regex only matched the DESCRIBE form
